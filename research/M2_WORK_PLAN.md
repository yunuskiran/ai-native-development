# M2 evidence-base work plan

Status: **RESEARCH-EDITOR PACKAGE PREPARED 2026-11-01; G2 REVIEW PENDING**. Authorized 2026-10-31 in A07. M1 architecture was accepted by the author in A06. Task acceptance criteria below remain binding; research evidence, completion and independent review are recorded separately. This plan itself contains no method scores or experiment results.

## Objective and deliverables

Build an inspectable evidence base for the accepted fourteen-chapter architecture before pilot prose. Deliver four method dossiers, shared history/SDD/technical evidence notes, a claim-and-source register with locators, contested claims, version/profile candidates, rights limits and an M2 review report. Keep source-described mechanisms separate from effectiveness evidence.

## Ordered tasks and acceptance criteria

| ID | Work / intended artifact | Acceptance criteria |
|---|---|---|
| M2-01 | Establish dossier records and revalidate source identities | Record actual retrieval/access dates and results; retain M0 snapshots as historical candidates. Every factual claim has ID, exact wording, source/URL, passage, scope, version, confidence, interests and unresolved limits. |
| M2-02 | BMAD dossier | Distinguish stable/preview and core/add-ons. Cover workflow, artifacts, decision rights, project variants and limits; every F01–F11 dimension supported by a primary passage or explicit gap. No registry/runtime inference from README alone. |
| M2-03 | GSD framework dossier and lineage note | Trace primary migration/history records; keep the selected framework separate from a coding-agent product. Recommend an edition scope with evidence; do not silently choose a lineage. Cover F01–F11 and context/window/host assumptions. |
| M2-04 | AWS AI-DLC dossier and concept/profile map | Separate original lifecycle from a defined implementation/version/profile. Identify required/optional ceremony, gate behavior, solo/team and local/operations boundaries with primary locators. Cover F01–F11. |
| M2-05 | AIUP dossier and adapter boundary | Verify core, use-case/artifact ownership, change/testing rules and the relevant TypeScript/Node implementation path. Distinguish documented adapter support from executed compatibility. Cover F01–F11 and equal limitations. |
| M2-06 | SDD/tooling evidence notes | Attribute the lifecycle terminology; inspect retention, ownership, code-edit and reconciliation policies for selected profiles. Keep toolkits/products as context and avoid a fifth trial arm. |
| M2-07 | History, independent comparisons and field reports | Source dated history/origin claims; read S17 beyond its abstract before using its rubric/results. Record first-hand tasks, versions, people, failures and conflicts. Preserve the absence of outcome evidence where applicable. |
| M2-08 | TypeScript/Node compatibility evidence matrix | Inspect current primary Node.js/TypeScript and selected adapters/hosts. Identify common supported configurations and uncertainty before recommending exact versions/framework/database. Do not install, run or purchase services merely to fill a documentation matrix. |
| M2-09 | Rights/originality evidence register | Inspect applicable licence/NOTICE/trademark sources for intended reuse; use lawful book access only if available. Record inaccessible full texts and unresolved permissions without asserting clearance. |
| M2-10 | Reconcile claims and comparison coverage | Every dossier dimension and planned factual section has evidence or an explicit gap. Keep contested sources, counterexamples and outcome claims visible; no intuitive rankings or invented measurements. |
| M2-11 | M2 report and technical-review handoff | Inventory inspected sources/versions, supported vs contested claims, limitations and remaining decisions. Update sources/tasks. Independent technical reviewer verifies support at G2; no automatic progression to prose. |

Research order begins with BMAD after the record structure, then GSD, AWS AI-DLC and AIUP. Shared source work may inform several dossiers, but independent evidence must not be inferred from repeated records in one source family. No delegated agents are required by this plan.
